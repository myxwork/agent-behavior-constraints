# Agent-Behavior-Constraints

> 一个纯 Markdown 的行为约束技能。装进 AI 之后，它会拦住"你没要求、也不是交付必需"的多余动作——多建文件、顺手重构、升级依赖、多跑几轮验证、多调几个角色、额外写总结报告。
>
> **无脚本、无依赖、不联网。** 装上就能用，删掉就干净。

---

## 1. 它解决什么

你只要求 A，交付出来是 A + B + C + D。三个典型症状：

| 症状 | 后果 |
|---|---|
| 只要改一处文案，同文件另外 12 处"顺手统一"了 | 改动面失控，review 成本比写代码还高 |
| 交付时多出 README、CHANGELOG、变更说明、总结 | 你要的东西被埋在一堆没人看的文档里 |
| 测试已经全绿，又完整跑了两轮回归；单文件改动还调了三个角色复核 | token 翻倍，工期拉长，质量并没提升 |

在多角色团队里这个问题会被放大：**上游多写的一章会进需求文档并编上号，下游默认它是你要的，于是照着实现**——越界就这样变成了规矩。

## 2. 它怎么工作

一句话：**每个动作先问三句，再决定做不做。**

```
① 用户说过要这个吗？          → 说过 = 必须做
② 不做的话，交付物还成立吗？   → 不成立 = 授权扩展
③ 是否新增了 文件/依赖/重复/扩面/新能力 任一？ → 是 = 越界
```

判定之后只有四种处理：

| 响应 | 什么情况 | 怎么做 |
|---|---|---|
| **直做** | 你要的；或不做就交不了；或白名单内 | 做，不打扰你 |
| **跳过** | 越界了，但完全可撤销、新增 ≤1 个文件、改 ≤2 处、不动主体外文件、不加依赖 | **不做**，交付时列一行告诉你 |
| **询问** | 越界且影响面更大；判不出来的也算这一档 | 一行字问你，回 `+` 或 `-`，**默认 `-`** |
| **停止** | 收不回来（升级已有依赖、删数据、改测试断言、改 CI、跨模块重构） | 直接停，做了就回退 |

> **判据全部可数**：几个新文件、几处改动、有没新增依赖。不用 token 估算——实测那玩意儿误差 4 倍，方向还不定。

配套四道闸：**开工锁范围 → 声明依赖 → 执行中判动作 → 交付前裁一遍**。

最后一道"交付前裁一遍"是兜底：即使前面全失守，你看到的东西里也不该出现没要求过的条目。

## 3. 两种编排场景

### 单智能体（自己派生子智能体）

直接用。它会在派生时判断"这个额外角色该不该调"。

### 预置团队（产品经理 → 架构师 → 工程师 → QA 固定链路）

这个场景**不改你团队原本的分工，也不改成员之间传什么**，只在两头加东西：

| 时点 | 加什么 |
|---|---|
| 派任务前 | **原话锚点表**：每条需求必须附用户原话，不许概括 |
| 收产物时 | **`[未溯源]` 标记**：成员可以多写，但你没说过的内容必须打标；**交接三问**：挂得上锚点吗 / 下一环必须做吗 / 剔除后还完整吗 |
| 交付前 | 逐条处置未溯源项 + 核对**链式放大比**（交付条目 ÷ 需求条目，≤2 正常） |

团队场景里不再数 token（数不出来），改数条目：**锚点覆盖率 100% / 放大比 ≤2 / 未溯源占比 ≤5%**。

> 按团队既定 SOP 走完固定角色链路，**不算越界**——豁免的是"流程规定的环节"，不豁免"环节内部的加码"。

## 4. 它明确不做的事

| 不做 | 原因 |
|---|---|
| 不判断"这个需求值不值得做" | 那是你的判断，不是它的 |
| 不压缩必要提问 | 靠猜来省 token，猜错就全错 |
| 不因省钱降低验证等级、跳过安全检查、修改测试断言 | 这是红线，没有例外 |
| 不生成任何"越界审计报告" | 反越界机制自身的产物就是越界物 |
| 不接管代码风格、架构规范、功能验收 | 它只管范围，不管质量细节 |

**红线优先于成本。** 遇到"省 token"和"做完主体要求"冲突时，永远选做完。

| 宿主 | 怎么装 |
|---|---|
| **WorkBuddy** | 解压后把 `agent-behavior-constraints/` 文件夹放进 `~/.workbuddy/skills/`（或项目级 `.workbuddy/skills/`） |
| **Claude Code** | 解压后把 `agent-behavior-constraints/` 放到 `<项目>/.claude/skills/` |
| **Claude.ai 网页版** | 设置 → 能力（Capabilities）→ 技能 → 直接上传 zip（zip 根目录就是 `agent-behavior-constraints/`） |
| **ChatGPT 自定义 GPT** | 把 `SKILL.md` 正文贴进 Instructions，`references/` 传到 Knowledge |
| **Cursor / Windsurf** | 转成 rules 文件：`.cursor/rules/agent-behavior-constraints.mdc`，去掉 YAML 换成 `alwaysApply: true` |
| **没有 skills 机制的聊天窗口** | 首条消息贴 `SKILL.md` 正文 + 一句"本次对话全程遵守，收到请回：已启用" |

**注意**：`SKILL.md` 正文用相对路径引用了 `references/` 下的文件，只贴正文会让索引失效。要保持目录结构。

### 让它稳定生效（重要，实测结论）

**它不是"装上就永远开着的开关"。** 这类"全局行为约束"和普通按需技能性质相反：按需技能是"遇到这类任务才调用"，而守卫需要**从任务第一秒就在场**——但技能的加载与否由宿主判断，不在你的配置里。

实测记录（WorkBuddy，2026-11）：

| 做法 | 结果 |
|---|---|
| 只把技能放进目录，不点名 | **没加载**（8–10 秒完成，无任何规则输出） |
| 在任务目录放 `AGENTS.md` 写明规则 | **无效**——WorkBuddy 没有"项目规则文件"机制（官方扩展能力只有 专家/技能/连接器/资料库） |
| 消息里加一句"按 agent-behavior-constraints 来" | **正常按规则执行** |
| 点名之后，后续十余轮不再点名 | **持续生效**——同一次会话内不会被"忘掉" |

所以按这个宿主的实际机制，可靠性排序是：

| 用法 | 怎么做 | 可靠性 |
|---|---|---|
| **① 贴常驻规则** | 把 [`assets/always-on-rules.md`](assets/always-on-rules.md) 的约 40 行贴进**专家提示**，或每个任务的**第一条消息** | 最高，每次都在场 |
| **② 点名一次** | 每个任务第一次开口说一句"按 agent-behavior-constraints 来" | 高，**一次管整段会话** |
| ③ 只靠自动触发 | 什么都不做 | **低，实测会漏** |

**推荐**：长期用 → ①；临时用 → ②。② 的成本比想象的低——**说一次就够，不用每轮重申**。

`assets/always-on-rules.md` 是专门为"贴进提示"做的精简版（约 40 行），不是技能文件的替代品——它保证最小可用行为（两栏清单、三问、两段交付输出），细节判定仍需读 `SKILL.md`。

另外一点：用户级目录（`~/.workbuddy/skills/`）和项目级（`.workbuddy/skills/`）只是**可见范围**不同，都**不代表自动执行**。

## 7. 已知局限（请先读这一节）

| 局限 | 说明 |
|---|---|
| **它是指令型，不是强制拦截** | 「停止」靠模型自觉遵守。真正的工具调用级阻断需要宿主 hook，不在本技能范围内 |
| **不设 token 预算** | AI 读不到真实账单，实测估算误差约 4 倍且方向相反 → 用它做判据只会误杀正常任务。判"有没有做多"看文件数、依赖数、重复次数 |
| **可逆性判断仍有主观余地** | 同一个动作，两个人可能一个判"可逆"一个判"不可逆"。清单给了 6 条硬边界，清单外按"不能无损撤销即停止"从严 |
| **团队场景指标是条目制** | token 分散在多个会话，数不出来。这是唯一能落地的口径，不是妥协 |
| **可能被误用为少做的借口** | 所以配了三条硬红线（主体覆盖率 100%、澄清永不拦、不降验证等级/不篡改断言）成对生效 |

**验证状态**（2026-11，WorkBuddy，共 11 轮灰度测试）：

| 项 | 结果 |
|---|---|
| 冒烟（只改一处 + 两段输出） | 通过 |
| 反向（要求"全面审查"不误拦） | 通过 |
| 红线（三件事一件不落） | 通过 |
| 不可逆动作（要求顺手删文件） | 通过——停下来问，文件保留 |
| 发散（要 10 个方向不收敛） | 通过 |
| **A2 / X 分界**（必要的新文件该建、多余的不建） | 通过——建 1 个 html，没建 README，并解释了技术限制 |
| **扩面**（只改一处，不顺手统一） | 通过——只改第 1 行，另 4 处原样，并主动提示跨文件不一致 |
| **灰区**（判不出来会问） | 通过——给了 2 个候选方向 |
| **团队派活** | 不在本技能验证范围（v0.17 起不管派活）；实测记录：首轮拉起 `mp-dev-engineer` 完成 9 文件，增量轮主理人自写 —— 属团队 SOP 的问题 |
| **「未溯源项」第三段** | 通过 1 例——报 `0` |

**未验证**：跨宿主一致性（换个 AI 判同一套行为是否同结论）。

> v0.19 为一致性修订（口径对齐，见 §10），上表为 v0.18 及以前的灰度记录；升级后建议重跑 §8 三分钟自检。

## 8. 三分钟自检

装上后，随便给它一个小任务，看四件事：

- [ ] 只改了你说要改的那一处
- [ ] 没多建任何文件
- [ ] 交付时出现「顺手未做项」（写"无"也算）
- [ ] 交付时出现「本次规模」，给的是**交付文件数与新增数**，不是 token、也不是预估

四项都对 = 生效了。再加一项反向检查：说"全面审查一遍，把所有问题列出来"——它应该直接开干，**不许反问范围**。这一项不过，说明规则把 AI 吓住了，比不装更糟。
