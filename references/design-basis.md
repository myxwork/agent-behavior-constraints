# 设计依据与决策记录

本文件说明规则为什么这样定。只在需要判断"某条规则能不能改"时读。

## 1. 设计原则

只有一条：**把"是否为用户所需"变成可机械核对的判断**，而不是靠"适度""合理"这类无法复核的词。

在此基础上补了第二条：**只用数得出来的东西当判据。** 数不出来的（token 估算）只做口头告知，不参与判定。

## 2. 已确认的 5 项决策

| 编号 | 决策 | 落地规则 | 现行口径 |
|---|---|---|---|
| Q1 | **混合制**：可逆且影响小的不做、只告知；影响大的问一句；不可逆停下 | SKILL.md §4 四级响应 | **判据从"≤3k token"改为可数条件**（1 个新文件 / ≤2 处改动），因为该估算实测误差约 4 倍且方向不定 |
| Q2 | **分类额度**：文件 +1 / 依赖 0 / 重复 0 | SKILL.md §4.0 | 删"成员 0"（属编排层）；**额度只管 A2**（不做就交付不了的必要增量），X 类不看额度——否则"补个没要求的文件"会被额度允许、被跳过禁止 |
| Q3 | ~~档位提案制~~：承接方报规模、用户可覆写 | ~~SKILL.md §5~~ → **已废止**（整节删除） | 一路收缩：token 数值 → 文件数 → **连文件数也不预估**。原因见 §5：估不准、不处置、会变成心理上限 |
| Q4 | **灰区**：判不出来怎么办 | SKILL.md §3.3 | **从"默认禁止"改为"问一句"**。禁止是隐形的，用户不知道；灰区本质是信息不足，问一句成本最低 |
| Q5 | **质量门槛**：澄清不限次数，但须给 ≥2 个候选；无效澄清只计数不拦截 | 红线 H2、`metrics.md` §2 | 无变化 |

这 5 条是骨架。改任何一条，要同步改 SKILL.md 正文、对应 references、本表——**一次全量体检发现的 23 条不一致，全部是"只改了一处"造成的。**

## 3. 已删掉的规则，为什么删

| 删掉的 | 原本干什么 | 为什么删 |
|---|---|---|
| 3k / 5k token 阈值 | 决定"跳过还是询问" | 估不准；用它做硬判定 = 用不准的尺子砍任务 |
| S/M/L 的 20k/120k/500k | 预算基准 | 同上；档位改为按文件数分，可数 |
| R、R_x、内部配比、单动作占比 | 成本核算 | 全部是 token 派生，读不到真实账单 |
| L0 vs L1 的区分 | 一个"只计数"、一个"记内部台账" | **两者对用户都不可见，且规则明令不生成台账文件** → 台账无处可写，属不可执行条款。已合并为「直做」 |
| W6 澄清白名单 | 澄清不算越界 | 与红线 H2、通道 A 重复定义同一件事，且"动作"与"响应"混在张表里 |
| S3 轮次码 | 区分"多叫一个人"与"多跑一遍" | 与 S2 判定和风险完全相同，导致同一动作被标两个码 |
| 「再叫一次已参与角色算越界」 | 防重复调用 | 属编排层，与 §1 自相矛盾；且紧跟「换谁上场你定」，被读成「再调同一角色要挨罚」，模型宁愿自己干 |
| 36 条对照表 | 覆盖边界情况 | 去重后 24 条，再删 2 条「成员过度」类，现存 **22 条**。被合并的是同形同级的重复行 |
| metrics 的"标定方法" | 校准阈值 | 阈值现在全是整数，不需要标定 |
| team-adaptation 的指标表 | 团队指标 | 与 SKILL §6.2.4 完全重复 |

## 5. 已知局限（必须知道，别当成能力）

| 局限 | 后果 | 缓解 |
|---|---|---|
| **是指令型，不是内核级拦截** | 「停止」依赖模型自觉；越界仍可能发生 | G3 交付前裁剪兜底；交付清单逐项可溯源、可被用户抽检 |
| 团队里规则只加载到主理人 | 成员内部的加码管不住 | §6.2 交接校验器：源头钉锚点、交接打 `[未溯源]`；成员只需诚实标注，不必自我审查 |
| 团队 token 分散在多个会话 | 任何 token 制指标都失效 | 已改为条目制（放大比 / 未溯源占比 / 锚点覆盖率） |
| 可能被误用为"少做"的借口 | 交付缩水 | 红线 H1/H3 + 质量侧指标成对生效 |
| **可逆性判断仍有主观余地** | 同一个动作，两人可能一个判"可逆"一个判"不可逆" | 不可逆清单给了 6 条硬边界，清单外按"不能无损撤销即停止"从严 |

真正的工具层阻断属于宿主 hook 的范畴，不在本技能范围内——本技能只提供判定与流程。

## 6. 口径裁决（同一规则只定义一次）

一轮全量体检（由外部进行，**报告未入库，故不引用具体条数**）发现大量"同一规则写在多处、改一处忘其余"的问题。下表只列**有实质裁决**的 9 项，其余为纯措辞对齐。修订原则：**每条规则只在一处定义，其余位置只放引用**。裁决如下：

| 事项 | 唯一定义处 | 裁决 |
|---|---|---|
| 「跳过」门槛 | SKILL §4.1 | 可逆 + 新增文件 ≤1 且改动位置 ≤2 + 不含 S2/S3 + 不改主体外文件。README / always-on / 对照表一律引用，不得复述变体（原三处口径冲突：SKILL 只允许 S1，README/always-on 允许"改 ≤2 处"，对照表 #8/#13 给 S5 判跳过） |
| 新增依赖响应 | SKILL §4.1 | 第 1 个询问，第 2 个停止；升级 / 降级已存在依赖 = 不可逆 → 停止（对照表 #5 原判停止，已对齐） |
| 询问未回复 / 额度满 | SKILL §4.1 | 一律"不做并记录"，不借用「跳过」门槛 |
| 构建失败豁免 | SKILL §7 | 已存在的构建 / 编译失败修复不计越界，是 W1 边界的唯一例外 |
| SOP 流程规定物 | SKILL §3.1 注 | 不算 S1；豁免规定物本身，不豁免其内部加码（原只在 team-adaptation，成员读不到） |
| 锚点「已取代」 | team-adaptation §3.1 + 锚点模板 | 修改需求 → 新增编号承接，旧编号标「已取代」；覆盖率分母不含「不做」「已取代」 |
| 脚手架豁免 | SKILL §4.0 | 以"逐项列出 + 说明不可省"为前提，未列出按 S1 |
| 「条目」计数 | SKILL §6.2.4 | 清单中一行 = 一个可独立核销的功能 / 文件 / 文档节 |
| A1 验收 | metrics §5 | 一致率 ≥90%，分歧须可归因到可逆性判断（已知主观项，见 §5 已知局限） |
| **列问题条数** | SKILL §3.0 | **不设上限**，超 5 条先问是否全列。原"≤5 条"是凭空数值，且会瞒报——问题客观有几个就是几个 |
| **主体内扩写** | SKILL §3.1 注 | 篇幅 / 条目 ≥ 需求 2 倍按 **S1** 计，仍算多做。原改判"无 S 码 / 灰区"，等于把"交付膨胀"移出越界范围，只剩下游放大比兜底 |
| **A1 归因权** | metrics §5 | ≥90% 保留，但**分歧归因由用户抽检确认，不由执行方自判**，否则该指标可自我豁免 |
| **规模预估** | SKILL §5 | **取消**：不预估 token，也不预估文件数。四条理由见 §5；改为只报"交付文件数 / 新增数"两个事后事实 |
| **先问后写** | SKILL §4.2 | 需要用户拍板的事，先问再展开；**不得把选项写成成品后再问**——写出来成本就付了 |
| **改为"先说明打算，再动手"** | SKILL §4.2 | 原口径"先问一句就停"两轮实测都对不上（模型稳定地"给一套方案 + 结果预览再问"）。改为三条硬边界：不产出文件 / 不同时铺开两套以上 / 关键歧义必须先问。**目的不变，只改措辞**——规则该描述有效行为，不该描述做不到的姿态 |

规则改动后建议做一次三分钟自检：给一个单点小任务（只改一处），看它是否①只改那一处 ②不多建文件 ③交付附「顺手未做项」与「本次规模」。三项都对，说明规则仍被执行。
