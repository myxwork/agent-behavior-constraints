# 预置团队适配细则（交接校验器模式）

本文件是 SKILL.md 第 6.2 节的展开。任务在多角色预置团队里执行时读。

**一句话定位**：不改团队原有的角色分工、不改成员之间传递的内容，只在**三个时点**做预防——派任务前钉住需求、收产物时挡住"洗白"、交付前逐条处置。

---

## 1. 为什么预置团队必须单独适配

同样一次越界，在单智能体里和在 4 人链路里，代价不是一个量级：

| 机制 | 表现 | 后果 |
|---|---|---|
| **成本是乘法** | 上游多写 3 章，下游要读 3 章并为它设计、再为设计写代码 | 上游多付 1 份，下游付 3–4 份 |
| **越界被洗白** | 上游多写的内容进了 PRD 并编了号，架构师不能删、工程师不能跳 | **下游没有任何人有权限撤销它**，只能实现 |
| **角色倾向** | 被调起来就要产出点什么，于是多设计一层、多测一轮 | 结构性副作用，不是模型不听话 |
| **转述加码** | 用户原话经主理人转述后变宽，且无人保留原话 | 加码后无从追溯，纠错成本极高 |

第 2 条是团队场景的核心风险：**单智能体的越界是动作，团队里的越界会变成制度。** 所以这里的首要目标不是"少做动作"，而是**"让多做的东西无法伪装成需求"**。

---

## 2. 三个预防时点

```
【时点一：派任务前】建锚点表 → 写进任务书 → 声明本环产出规模
        ↓
【时点二：收产物时】三问校验 → 打 [未溯源] → 剔除或降级
        ↓
【时点三：交付前】逐条处置未溯源项 → 核对放大比 → 出交付说明
```

四个环节的链路，一共做 3 次时点一、4 次时点二、1 次时点三。**不对每个动作逐一裁决。**

---

## 3. 时点一：原话锚点表

### 3.1 规则

| 项 | 规则 |
|---|---|
| 谁建 | 主理人在派第一个任务之前建，后续只增不改 |
| 最小字段 | 编号 / 需求条目 / 用户原话片段 / 状态（待做·已交付·已剔除） |
| 出处要求 | 原话片段必须是用户真实说过的话，**不许转述、不许概括** |
| 覆盖要求 | 用户提过的每一条主体要求都要有编号；用户明确排掉的也要记（标"不做"） |
| 后续变更 | 用户中途**追加**需求 → 新增编号，不许改旧编号的含义；用户中途**修改**需求（非追加）→ 新增编号承接新含义，旧编号标「已取代」并注明承接编号，不计入覆盖率分母 |

### 3.2 为什么必须带原话

只写"需求条目"时，条目会随转述逐级漂移：用户说"改一下文案"，PM 写成"优化文案一致性"，架构师理解成"建立文案规范"，工程师做出一个文案管理模块。**带上原话，漂移就看得见。**

### 3.3 写进任务书

锚点表不能只存在主理人脑子里，必须**随每次派任务传给对应成员**（只传相关条目，不用传整张表）。

---

## 4. 时点一：委派任务书（四段式）

不用改成员之间传递的产物，只改**你派活时说的那几句话**。固定四段：

```
① 本环只负责：R1、R2（照抄原话）
② 本环不做：R3（用户明确排掉）；以及任何新增功能、新增依赖、新增文档
③ 超出 R1/R2 的任何内容，写了要标 [未溯源]，不标视为违规
④ 交付格式：产出 + 一句话说明哪些内容未溯源
```

第 ③ 段是关键：它把"是否越界"的判断从"主观"变成"有没有标"。**成员不需要判断什么算越界，只需要诚实标注。**

模板见 `assets/anchor-ledger-template.md` 第二节。

---

## 5. 时点二：`[未溯源]` 标记

### 5.1 格式

紧跟在条目、章节标题或文件说明之后，独占一个标记：

```
**示例：未来扩展预留在产物里长什么样**
```

### 5.2 处理矩阵

| 角色 | 看到 `[未溯源]` 该怎么做 |
|---|---|
| 下游成员 | **不实现、不扩展**。可以引用作为背景，但不得当作必做项，不得为它再加设计 |
| 主理人（收产物时） | 逐条判定：删除 / 降级为"建议" / 补授权（问用户） |
| 用户 | 只在交付说明里看到汇总，不被逐条打扰 |

### 5.3 三条反滥用规则

1. **不许全标**：如果一份产物 80% 都是 `[未溯源]`，说明任务书第 ①② 段没写清，问题在主理人，不在成员。
2. **不许不标**：漏标等同于越界，且比越界更糟——因为它伪装成了需求。
3. **标记不改变归属**：标了也仍然是"用户没要的东西"，交付时不能因为"标过"就算合规。

### 5.4 例外

A1 类必要动作（不新增交付物的必要步骤，如修自己引入的编译错误、跑定向验证）不需要标记。

---

## 6. 时点二：交接三问

主理人每收到一份产物，问三句，30 秒内完成：

| # | 问 | 判断依据 | 处置 |
|---|---|---|---|
| ① | 哪些内容挂不上锚点编号？ | 逐节扫标题与要点，找不到对应 R 编号即为挂不上 | 标 `[未溯源]` |
| ② | 挂不上的，下一环必须做吗？ | 不做的话，R 编号里的条目还能交付吗？ | 不能不做 → 补进锚点表并说明来源；不是必须 → 不进下一环的必做清单 |
| ③ | 剔除后主体还完整吗？ | 对照锚点表逐条核销 | 不完整 → **上游漏项，回退补齐**，不得用新增内容顶替缺口 |

第 ③ 问最容易做错：发现少了东西时，人的本能是"让下游顺便补上"，那就变成了新的越界。**漏项要回到产生它的那一环去修。**

---

## 7. 时点三：团队专属的三项处置

1. **逐条处置未溯源项**：删除 / 降级 / 补授权。一条都不许留在交付物里当作既有成果。
2. **核对放大比**：末环交付清单条目数 ÷ 锚点表主体条目数。2–3 在交付说明加一句主要来源；>3 说明链路中间膨胀了，回头找是哪一环。
3. **出交付说明**：主体交付物 + 「顺手未做项」+「本次规模」+ 一行「返工 N 轮 / 未溯源项 N 条」。

## 8. 度量

指标定义与阈值只在 `SKILL.md` §6.2.4 与 `metrics.md` 第 3 节定义一次，本文件不重复——**同一张表写两遍，改一处必忘另一处**（一次体检里，23 条不一致中有 4 条就是这么来的）。


## 9. 与团队 SOP 的边界

角色与流程本身不归本技能管（见 SKILL.md §1）。只有两处需要说明：

| 情形 | 判定 |
|---|---|
| 按既定 SOP 调起成员、复核、返工 | 不判。属编排与流程，见 SKILL.md §1 |
| SOP 规定要产出 PRD 全文 / 架构文档 | 不算 S1 新产物。定义见 SKILL.md §3.1 注，此处引用不复述 |
| 某个角色被复核几遍、返工几轮 | **不判**。属编排与流程，见 SKILL.md §1 |

一句话：**角色怎么调、调几次，本技能一概不判；它只判每个成员手上那一步该不该做。**


## 10. 常见误用

| 误用 | 后果 | 正确做法 |
|---|---|---|
| 用 `[未溯源]` 洗白越界 | 标了就当合规，越界合法化 | 标记只是留痕，处置权在主理人，标了仍要删 |
| 交接三问变成逐条审稿 | 主理人成了第二个人工审稿岗，链路更慢 | 只扫标题与要点，30 秒，不逐字读 |
| 发现漏项就让下游补 | 缺口变成新越界 | 回到产生缺口的那一环修 |
| 把放大比当 KPI 压到 1 | 架构与设计被砍光，交付质量下降 | 放大比是"警报器"不是"目标值"，>3 才动手 |
| 任务书四段只写第 ① 段 | 成员不知道边界在哪 | 四段齐全，尤其第 ③ 段（标记规则） |
| 团队场景仍按 token 比核算 | 数不出来，指标形同虚设 | 改用条目制指标 |

## 11. 一个完整走查（示例）

**用户原话**："给这个名单加个导出，导出成表格，只要名字和电话两列。"

**锚点表**

| 编号 | 需求条目 | 原话 | 状态 |
|---|---|---|---|
| R1 | 增加导出功能 | "加个导出" | 待做 |
| R2 | 导出格式为表格 | "导出成表格" | 待做 |
| R3 | 只含名字、电话两列 | "只要名字和电话两列" | 待做 |

**第 1 环（产品经理）**：任务书四段 → 产出需求说明。
收产物时发现它写了"未来支持导出 PDF / Excel 自定义模板"两节 → 标 `[未溯源]` → 第 ② 问：下一环必须做吗？不必 → 不进下一环必做清单。

**第 2 环（架构师）**：任务书只列 R1–R3 + 明确"未溯源内容不实现"。产出架构说明，若仍写了扩展点设计 → 同法标记。

**第 3 环（工程师）**：只实现三列导出 + 一个入口按钮。
若它顺手加了"导出进度条" → 这是动作级越界，按「跳过」处理并记入「顺手未做项」。

**第 4 环（QA）**：只验证三列是否导出正确、格式是否为表格。多跑一轮全量回归 → S2 重复，判「询问」。

**交付前**：3 条锚点全部核销（覆盖率 100%）；交付清单 1 个功能 + 1 个入口（放大比 = 2/3 ≈ 0.7，正常）；未溯源处置：删除 2 节、降级 1 处；规模 M 档：预计 4 个文件，实际 4 个，一致。

**如果没做这套**：这一单很可能交付 6 个文件（含 PDF 导出、模板管理、导出配置），放大比 2.0 以上，且那 3 个多余能力会被后续任务当成"已有功能"继续维护。
